# 第二批公开评测与修复记录

本轮继续使用 CLAMBER、LongMemEval oracle 中未进入首轮的记录，先冻结选择清单和既有评分标准，再观察失败、作通用修复和本地提交。原始结果和失败均保留，未修改标签或通过条件。首轮记录见 [EVALUATION_RESULTS.md](EVALUATION_RESULTS.md)，运行方式见 [EVALUATION.md](EVALUATION.md)。

## 样本与运行环境

新增 38 条公开样本：CLAMBER 24 条，覆盖六个类别/标签分层；LongMemEval oracle 14 条，覆盖七种问题类型，保留完整的 10–24 条历史消息。选择按固定哈希排序，每层平均划分开发/初始留出，排除首轮 ID 和共享证据历史的普通/abstention 对。不是按结果挑选，也不是优先最短历史。

原始数据文件 SHA256、前序清单 SHA256、预检排除 ID 和冻结选择保存在 `tests/fixtures/evaluation_expansion_selection_v1.json`。包含晚于问题日期历史的 43 条 oracle 记录仍按同一预检规则排除。开发和留出在第一次被观察后均成为后续修复证据，不能再称未见测试。

模型仍为配置的 `deepseek-chat`（响应记录为 `deepseek-flash`），Embedding 为本地 Ollama `bge-m3:latest`，评分为协议 1 的自定义 DeepSeek 独立调用。不是官方 LongMemEval GPT-4o 分数。本轮没有运行完整 LongMemEval S/M，也没有声称完成 CLAMBER 3202 条或 oracle 500 条全集。

所有运行使用公开或合成对话、独立的临时记忆目录。没有读取或提交用户实际记忆。CLAMBER 只验证意图与澄清，生成 GoalSpec 不算实际执行成功；记忆和建议样本按契约检查真实执行结果。

最初 file-only 执行环境导致需要公开资料的建议无法完成。本轮随后冻结 `public-live-readonly-v1` 环境，显式启用已有 Tavily 只读搜索；缺少配置会报 setup error，不静默回退。两种工具环境的成绩单独保留，不把环境变化算作同环境修复提升。中文天气仍使用固定响应。

## 标签、策略与评分分歧

这些问题仍按冻结协议计为失败，不能通过人工解释改写成绩。

- `clamber-2050` 的共同类别前提与示例不相符。产品曾漏掉冲突，属于真实缺陷；修正后应要求更正材料。评分提示同时要求输出 X/Y 和另一种参考澄清，可能把必要修正问题判错。两者应分别记录。v4 虽最终提出澄清，但其共同条件分析的解释仍有逻辑错误；不能把这一条全部归因于评分器，也不能声称推理问题已彻底修复。
- `clamber-0191`、`clamber-0278` 的标签要求用户解释精确公共名称；当前策略是按原名先核查身份/资料，避免要求用户先提供研究答案。这是策略与标签分歧，不能据此声称原标签错误。Alacia valdiviae 的公共记录可见 [ITIS](https://www.itis.gov/servlet/SingleRpt/SingleRpt?search_topic=TSN&search_value=684300)。
- `clamber-2759`、`clamber-2664` 标为无需澄清，但代词存在多个合理先行词，产品要求唯一事件指代。属于待审定的标签疑点，本轮保留原标签。
- `clamber-0997` 的“当前 iOS”参考澄清列出旧年份；产品有可信当前时间，能够直接查询当前版本。不能为匹配旧参考强行要求用户选年份。
- `clamber-1132` 的固定评分曾把需要澄清的演员/角色问题当作需要实际演员答案，随后也出现候选澄清范围与参考不匹配。不能把所有失败都归因于评分器，更不能直接人工改成通过。
- `clamber-1174`、`clamber-0730` 涉及多个作品版本或发言范围。本轮允许可完整并列回答的兼容解释；是否必须先选一个属于应单独审定的业务边界。

如果后续修改判定标准或评分提示，需建立新协议和新基线，不能覆盖这些原始结果。

## JSON 输出模式与评分隔离

提示词闭合说明和一次修复未能稳定消除多余括号。当前产品调用显式使用 DeepSeek 的 `response_format={"type":"json_object"}`，通过现有 LangChain 封装和执行库已提供的 opt-in JSON mode 接口。官方行为说明见 [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。实际安装封装的合成 API 探测验证该模式可用，保留在 `json-mode-compatibility-probe-v1.json`；它是兼容性探测，不计入正式成绩。

该模式要求 JSON 语法有效，不保证业务正确或 schema 满足。严格解析仍拒绝多余结束符，原有 schema 校验和失败反馈继续生效；没有截取第一个 JSON 值或自动丢弃尾部。HTTP mock 同时验证 JSON object 请求、非法尾部拒绝以及评分器原有 function calling 请求。

评分器继续使用协议 1 的原模型、原提示词和 **function_calling** 传输方式，产品模式变化不修改评分器。代理与评分器使用不同客户端，标准答案仅提供给评分器，双方调用和实际模式都保存在结果中。这个边界另有离线端到端测试，验证标准答案未进入代理输入、评分调用仍记入总调用记录。
