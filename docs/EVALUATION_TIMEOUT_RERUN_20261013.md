## 二、LongMemEval 两条失败：原因已经具体定位

### 1. a4996e51：引用被改写，修复后仍不忠实

阶段为历史写入，错误为 MemoryFlushError，底层 MODEL_RESPONSE_INVALID。
并非 JSON 无法解析：模型输出通过了结构解析，但来源核对失败。

用户原文为 `could help me update my resume and LinkedIn profile ...`，模型生成的引用却是
`help you update my resume and LinkedIn profile ...`，把 me 换成 you。
程序返回 INVALID_SOURCE_QUOTE，并提供了出错事件、pointer 和 quote；修复输出仍包含
`could help you update ...`。同一源事件在上一轮也失败。

m3 原文已持久化；该事件的派生记录失败，索引 pending；评测的 flush 因失败中止，没有进入
问题回答。不能说记忆整体消失，也不能把该错误归因于召回或模型请求超时。

**原因：模型改写了必须逐字保留的证据，单次生成修复未纠正；事件级写入失败进一步
阻断了完整评测流程。校验拒绝错误引文是必要保障，不能通过放宽原文匹配消除错误。**

建议：将事实生成与原文定位分开，尽量由程序根据已验证的来源定位提取原文；修复只处理
出错证据而非重写整个抽取结果。证据仍须严格核验，不能模糊匹配后悄悄替换主客体。
若未来允许部分写入，应显式标记不完整并保留失败状态，不能把缺失当作完整写入成功。

trace 证据：`memory.model_repair` 事件 `e523ef51e28d4e9d85e71e57ddba5edd`，修复响应
`7f0d084642a2453cac2d9ed3918dba7a`；源事件
`bb4e357038909eccd9d89b0e32b2f3b182e5d7e7f5ff375a9aa62d12c490d4b5`。

### 2. 75832dbd：正确召回后，被额外覆盖项卡住

本轮已经识别用户研究方向并生成目标，失败发生在 `intent_goal_review`，未进入 DAG 执行。
程序要求覆盖 6 个指定 evidence_id；模型返回全部 6 个，额外再写入 1 个来自真实召回包的
ID `370608935b085fd582ef2d2c60b00cd8`，并将其标为 `not_applicable`。

额外项是一条相关性为 uncertain 的 m2 用户来源记录，不属于程序只选取 relevant 记录
形成的清单。它不是编造 ID，也不是漏掉 6 项中的某项。但 `_check_evidence_coverage`
将多项、漏项等情况统一报为 INCOMPLETE_EVIDENCE_COVERAGE。

修复请求只提供这一笼统错误；模型重写完整目标后仍返回相同的 7 项，再次被拒绝。
**原因：模型没有遵守精确 ID 清单，加上校验反馈未区分缺项、额外项和重复项，无法指导
针对性修复。它不证明记忆未召回或模型不理解研究领域。**

建议：保留精确清单契约，同时反馈 missing_ids / unexpected_ids / duplicate_ids 和
合法 ID 集合。先让修复准确删去额外项，不必重写已正确的业务目标。不能为了通过测试
直接接受未知来源或静默跳过证据校验。

trace 证据：第一次响应 `d5ae37baf20046398ea387480a4962c5`，修复请求
`8f2a4e8bd2174008a714342d908c92b1`，第二次响应 `9879101fc9e54896af6559943254af23`。

### 明确的判断错误：合理阻断被审查撤销

`clamber-2050` 的初评识别第一个示例不满足两种候选类别中的任何一种，因而两个示例无法
共享类别；后续审查没有给出兼容条件，只声称两项要求可同时成立并清空冲突。
Karen 随后生成仍要求推断共同类别的目标。这里有实质矛盾未解决，不能当成单纯标签争议。

初评事件 `f4204e3a35eb422eb6b530570f81309f`；审查事件 `b0526b4a97e44df2bbfc0edbd80ba38b`。

建议：撤销已识别的冲突应指出原文中能同时满足要求的条件或解释，校验针对原疑点；
不要让审查重新独立决定整个任务，也不要简单删除全部审查。该通用机制仍需成对验证，
不能只给本题新增答案规则。

### 审查标准过严与标签争议需要区分

当前提示词要求“有不同于待解析句子的直接声明”，并排除仅按常见语义消解。
对 `clamber-2759`，这会推翻初评基于因果语义的正常推断，导致追问。
`clamber-2664` 的原句确实缺少明确唯一指代，其公开标签为不追问；产品可能更适合直接
说明无法唯一确定，而不是向用户索要答案。不能强行把其中一个名字写成正确答案。

建议：分别定义“理解文本中的指代”与“确定会执行操作的对象”的证据要求。分析型回答
可呈现歧义或合理推断；高影响操作仍需要充分定位。这应是一条通用产品规则。

### 查证、默认和并列覆盖与公开标签不一致

公共查证或并列回答可能是合理产品行为，但也可能掩盖真正的目标歧义。
特别是 Zis，仅凭它是一个名称不能保证查证可定位用户意图；The Conjuring 也不能只凭
单一候选就证明用户指的是 2013 版。当前 CLAMBER 适配器只测意图，生成 GoalSpec
不证明已经完成查证或交付，因此本轮不能把这些 failed 自动改为产品 passed。

建议：用独立冻结的产品标签评价“是否应查证/默认/并列回答”，同时保留 CLAMBER 原标签。
对查证路线再评价查证后的实际交付及无法定位时的后续行为，避免只看不追问率。

## 四、预算变化起到了什么作用

本轮清晰度、回答、目标各自生成及审查共享 120 秒；精排含重试 90 秒；召回整体 180 秒。

- `b6019101` 精排两次约 25.36 + 47.12 = 72.48 秒；`caf03d32` 约 27.46 + 44.65 = 72.11 秒。
  二者超过旧 60 秒精排上限，实际使用到了新预算，最终通过。
- 二者本轮回答/清晰度阶段均在旧 60 秒内完成，因此不能断言它们的最终恢复完全由
  意图阶段 120 秒预算带来；模型输出和负载波动也会影响结果。
- 仍有 8 次精排输出截断记录。`0e4e4c46` 扩预算重试后精排仍耗尽约 90 秒，融合降级后
  正确回答。这证明最终无超时错误不等于内部没有超时。
- 12 个已返回记忆的交互中，7 个出现精排输入预算裁剪、6 个上下文预算裁剪、9 个详情
  预算限制，1 个发生精排失败降级。类别可重叠，不代表对应回答都失败，也不能覆盖未返回
  交互结果的两个错误案例。

未发现最终评分失败。来源校验与 ID 校验的失败均不能靠继续延长超时解决。
本轮无需再次普遍增加预算，优先处理上述确定性反馈与审查决策问题。

## 五、结论与后续优先级

1. **先修精确 ID 覆盖的错误反馈**：失败机制明确，改动可限制在校验和修复边界，保留安全契约。
2. **再提高来源引用修复可靠性**：原始证据正确且已持久化，避免 LLM 在修复时反复改写原文。
3. **单独做澄清审查的对照实验**：同时覆盖“误撤销真实冲突”和“过度阻止语言推断”两个方向。
4. **产品标签与公共标签并列报告**：不能用场景专用规则追求这 24 条的标签匹配，也不能把
   所有标签差异都解释为数据不合理。

这轮证据更支持“多个可定位的接口、反馈及判断标准问题叠加”，尚不足以判定必须推翻
LangGraph/DynamicAgentGraph 架构或更换模型才能解决。
