# 第一版异步任务管理

`karen.task.TaskManager` 管理同一进程内的任务；CLI 与个人微信使用相同的 `TaskInteraction` 命令入口。理解、澄清和记忆读取可以并发推进；实际执行继续由 DynamicAgentGraph 完成。

## 使用

默认同时推进 2 项任务，可通过 `--max-concurrent-tasks N` 调整，N 必须为正整数。CLI 与 `--wechat` 均适用。最多允许 32 项排队中的输入推进，超过时明确拒绝，不静默丢弃。

- `/new 内容`：创建独立任务，即使当前有待回答问题。
- `/tasks`：查看任务编号、状态和请求摘要。
- `/use ID`：选中任务，后续普通输入归入该任务。
- `/reply ID 内容`：明确回复任务，通常用于回答澄清。
- `/cancel ID`：取消排队、运行中或等待回复的任务。
- `/help`：显示命令帮助。CLI 的 `/exit` 退出并取消未完成工作。

尚未选择任务且存在待回答问题时，普通输入先保留；使用 `/use ID` 后直接投递这条输入，不要求重复输入；若它是新请求，可直接输入 `/new` 将保留的输入建为新任务。没有待回答问题时普通输入创建新任务。第一版不使用模型猜测消息归属，也不假定微信提供了可靠的引用消息 ID。运行中的任务暂不接受中途修改，应等待、取消，或另建任务。

任务完成后的明确后续回复创建新任务，保留 Karen 已有的来源结果反馈关联；不会覆盖已完成任务的结果。失败任务不自动重放。

CLI 输出带任务编号。`--json` 输出 JSON Lines：`type=notice` 表示入口反馈，`type=task` 表示任务事件，其中 `state` 为机器状态，执行结果位于 `result`。不同任务的完成顺序不保证与输入顺序相同。终端编辑使用异步输入和受保护的输出，后台结果不会作为用户输入读取。

## 生命周期与隔离

状态包括 queued、running、waiting、completed、failed、cancelled。每个任务拥有独立 IntentSession、请求 ID、澄清台账、原始时间基准及取消信号；对话来源保留，但不会自动复制其他任务的会话历史。等待回复后释放并发名额；同一任务的两轮推进不能同时启动。

第一版采用保守的共享资源策略：同一个 Karen 实例的执行器运行串行化，覆盖规划、工具与模型执行，避免执行器任务之间同时修改共享目标。并发上限控制完整任务推进，不代表同时执行 N 个工具图；等待执行锁的任务仍占推进名额。这不是文件路径级锁或跨进程锁，也不提供跨任务读取顺序、外部程序修改或文件覆盖冲突的语义判断。更细粒度的资源调度不在本版范围内。

取消既发出执行器取消信号，也取消当前推进协程，并等待其退出后释放名额。已产生的文件、网络请求等副作用不会回滚，不能据取消状态断言所有外部操作均未发生。

## 微信交付与退出

接收、执行和结果交付分别运行；处理新消息不等待旧任务执行完成。每轮任务结果关联触发它的原始消息及回复 token，不借用最近收到的其他消息。收件箱在最终结果保存前保持 running；接收通知走 progress outbox，不冒充任务完成。已保存结果、附件及传输重试沿用原有事务 outbox，重试发送不会重新执行任务。

任务调度本身仍在内存中，暂不提供完整任务持久化、失败继续或多任务重启恢复。保留微信原有的最近一次单会话澄清检查点；它不等于恢复全部任务，恢复后任务编号会重新分配。进程中断的运行记录按既有机制报告结果不确定，不自动重做。

CLI 的 EOF 等待已接收推进结束并交付结果；`/exit` 或取消关闭任务管理者，再关闭流程发现、记忆和观测组件。正常退出仍等待既有持久化组件完成写入。

## 接口与观测

`submit(text, session, task_id=None, received_at=None, source=None)` 返回任务；`cancel(task_id)` 取消；`events` 提供带来源的状态结果；`close()` 停止接收、取消并等待工作退出。渠道负责展示和实际交付，任务管理者不直接发送消息。

`task.state` 记录任务状态与错误码，`task.turn` 将一次推进与后续输入、召回、模型和执行 trace 关联。用户文案集中在 `message/messages.py`。不引入新的模型角色、外部消息服务或任务数据库。
